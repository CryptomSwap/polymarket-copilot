# Polymarket Data Coverage Audit

Code-grounded audit of what Polymarket-related data we fetch, store, normalize, and expose. Focus: data completeness and UI trustworthiness without large architectural change.

**Audit scope:** Market sync, user sync (orders/fills/positions), portfolio recompute, positions API, recommendations inputs, market/news linking. All references are to actual code paths in this repo.

---

## 1. Upstream entities we touch

| Entity | Source | Used in |
|--------|--------|---------|
| **Markets** | Gamma API (`gamma-api.polymarket.com`) | Market sync → `SyncedMarket` + `SyncedAsset` |
| **Assets / tokens** | Gamma (per-market `clobTokenIds`, `outcomes`) | Stored as `SyncedAsset` (tokenId, outcome, outcomeIndex) |
| **Open orders** | CLOB L2 (`clob.polymarket.com` GET `/orders`) | User sync → `UserOrder` |
| **Trades (fills)** | CLOB L2 GET `/data/trades` | User sync → `UserFill` |
| **Positions** | Not fetched directly | Reconstructed from fills in user-sync (`UserPosition`) and from fills again in portfolio engine (`DerivedPosition`) |
| **User connection / auth** | Stored credentials (`PolymarketApiCredential`), `ConnectedWallet` | `getStoredCredentials()`, `getFunderForRecompute()` |

We do **not** call a dedicated “positions” endpoint; positions are derived from fills (and optionally from open orders for reserved size).

## 2. Current fetch sources / endpoints

| Flow | Endpoint / source | Code |
|------|-------------------|------|
| **Market sync** | `GET https://gamma-api.polymarket.com/markets?limit=&offset=&active=true&closed=false` | `lib/polymarket/markets.ts` – `fetchGammaMarketsPageRaw` |
| **Orders sync** | `GET https://clob.polymarket.com/orders` (L2 auth) | `lib/polymarket/l2-readonly.ts` – `fetchOpenOrdersL2` |
| **Fills sync** | `GET https://clob.polymarket.com/data/trades` (L2 auth, `next_cursor=MA==`) | `lib/polymarket/l2-readonly.ts` – `fetchTradesL2` |
| **Credential validation** | `GET https://clob.polymarket.com/auth/api-keys` (L2 auth) | `lib/polymarket/l2-readonly.ts` – `validateCredentialsWithClob` |

**Limitations in code:**

- Orders and trades use a single page only (`next_cursor=INITIAL_CURSOR`); no pagination loop. Large histories are truncated.
- Market sync is paginated (default 100 per page, 5 pages max) and can be run with `activeOnly: false` for backfill.

## 4. Fields exposed to API / UI

- **GET /api/portfolio/overview**  
  Latest `PortfolioSnapshot`: totalOpenExposure, totalReservedExposure, realizedPnl, unrealizedPnl, openPositionsCount, openOrdersCount, topThemeConcentrationPct, topMarketConcentrationPct, yesExposure, noExposure, createdAt.

- **GET /api/portfolio/positions**  
  `DerivedPosition` rows with enrichment: marketId, marketTitle, marketSlug, category, theme, endDate (from SyncedMarket), decision snapshot, diagnostics (matchedByMarketId / conditionId / assetId, unresolved count).

- **GET /api/portfolio/intelligence**  
  Full intelligence object: summary, concentration by market/category/theme, timeline (nearResolution, agedPositions), flags, actions, diagnostics, unresolvedEnrichedPositions (with endDate/hoursToEnd).

- **GET /api/portfolio/behavior-flags**  
  `BehaviorFlag`: type, severity, marketTitle, description, metadata, createdAt.

- **GET /api/markets**  
  SyncedMarket: id, slug, title, status, category, endDate (filtered by status/endDate, limit 100–500).

- **GET /api/markets/[slug]**  
  Market by **slug**; detail includes market, outcomes (from assets + raw prices), price snapshots, signals, recommendations, positions (by assetIds), fills, orders, behavior flags, notes, news links. Positions/fills/orders are joined by assetId and funder.

- **Dashboard / portfolio UI**  
  Consumes overview, positions, behavior-flags, intelligence. Portfolio page uses `position.marketId` and `position.assetId` for alerts and linking. Market detail page uses **slug** in URL and fetches by slug; all downstream data uses `market.id` (our internal id).

## 5. Known fragile mappings (market id vs conditionId vs assetId)

### 5.1 Three different “market” identifiers

1. **SyncedMarket.id** – Our primary key (cuid). Used in: DerivedPosition (after resolution), MarketSignal, MarketNewsLink, Portfolio/Intelligence, market detail API, preflight.
2. **SyncedMarket.conditionId** – From Gamma; often what CLOB returns as `market` on orders/trades.
3. **SyncedMarket.slug** – From Gamma (or fallback conditionId); unique, used in URLs and market detail GET.

User-facing and internal links use **slug**. Joins with orders/fills/positions often need **id** or **conditionId** because:
- **UserFill.market** and **UserOrder.market** are the raw CLOB field (not our id).
- **DerivedPosition.marketId** is set to our id when resolution succeeds, otherwise remains the fill’s `market` (conditionId). So **DerivedPosition.marketId can be either our internal id or a conditionId** depending on resolution.

### 5.2 Resolution chain (code reference)

- **lib/polymarket/portfolio.ts**  
  - `resolveMarketRef(ref)`: tries SyncedMarket by **id**, then by **conditionId**.  
  - `resolvePositionToMarket(marketId, assetId)`: tries (1) marketId as SyncedMarket **id**, (2) marketId as **conditionId**, (3) **assetId** via SyncedAsset → SyncedMarket.

- **lib/polymarket/portfolio.ts** – `derivePositionsFromFills`:  
  - For each asset, metadata comes from SyncedAsset (tokenId → our market id/title) or, if missing, from `resolveMarketRef(agg.marketId)` where `agg.marketId` is `f.market` from fills.  
  - So if CLOB returns conditionId in `market`, resolution succeeds when we have a SyncedMarket with that conditionId; then we store our internal id in DerivedPosition.marketId. If resolution fails, we store the raw string (conditionId) and marketTitle can be "Unknown market".

- **app/api/portfolio/positions/route.ts** – `enrichPositionsBatch`:  
  - For each position, enrichment tries: marketId by **id**, then by **conditionId**, then by **assetId** (SyncedAsset → market). Returns marketSlug, endDate, etc., and diagnostics (matchedByMarketId / conditionId / assetId, unresolved).

### 5.3 Where this hurts

- **Portfolio/positions UI:** If a position’s market wasn’t synced (or slug/conditionId mismatch), `marketId` may be conditionId. Links to “market detail” need **slug**; the positions API returns `marketSlug` only when enrichment resolved. So a position with unresolved market has no marketSlug and cannot link to `/markets/[slug]` without an extra resolution step.
- **Alerts / drift:** Drift and alerts key by `marketId` and `assetId`. If `marketId` is conditionId for some rows, grouping or lookup by our internal id can miss them unless we resolve again.
- **Recommendations / news:** Recommendations and news influence use **SyncedMarket.id** (from signals and MarketNewsLink). So they are consistent internally, but any UI that shows “your position in this market” must join on our id or resolve conditionId → id.

## 6. Missing but high-value fields for serious trading workflow

(Inferred from current schema and usage; no speculation beyond what the code implies.)

- **Resolved market identifier on positions:**  
  Positions (and optionally orders/fills) would benefit from storing **both** the raw CLOB `market` and our **SyncedMarket.id** (and optionally slug) once resolved, so UI and APIs don’t depend on re-resolving and we can always link to market detail.

- **Pagination for orders/trades:**  
  L2 fetch is single-page only. For full history and accurate cost basis, pagination (and/or date filters if the API supports them) would reduce truncation risk.

- **Realized PnL at position level:**  
  `DerivedPosition.realizedPnl` is written as `"0"` in `derivePositionsFromFills`. Realized PnL would require either CLOB history of closed positions or a separate notion of “closed” and summing fills that net out.

- **Last trade / last fill timestamp on position:**  
  We have `openedAt` (first fill). A “lastActivityAt” or “lastFillAt” would help for aging and “near resolution” UX without re-scanning fills every time.

- **Market-level liquidity/volume freshness:**  
  We store `volumeNum` and `liquidityNum` from Gamma at sync time. For “can I trade this size?” we don’t have a live or recently updated liquidity view; market snapshots are for price, not order book depth.

- **Explicit “resolved” / “closed” for markets:**  
  We normalize status and endDate, but there’s no explicit “resolved” boolean. Resolution state matters for positions and for hiding resolved markets from “active” lists.

## 7. Suggested canonical identifiers and view models

- **Canonical market reference in app:**  
  Treat **SyncedMarket.id** as the canonical internal reference. Where we accept external input (e.g. CLOB `market`), resolve once to SyncedMarket.id (and optionally slug) and store that on the record (e.g. DerivedPosition, or a small resolution cache) so downstream code never has to guess whether a string is id or conditionId.

- **Canonical position view:**  
  A single “position with market” view that always includes: our market id, slug, conditionId (for external APIs), marketTitle, endDate, and at least one stable identifier (e.g. assetId + funder) for dedup. Today the positions API approximates this via enrichment; making “resolved market id + slug” first-class on DerivedPosition (or a companion table) would simplify APIs and UI.

- **Slug for deep links:**  
  Keep using **slug** for user-facing URLs (`/markets/[slug]`). All responses that need a “go to market” link should expose `marketSlug` when available; when enrichment fails, either hide the link or resolve conditionId → slug in a dedicated step.

## 8. Quick wins vs later improvements

### Quick wins (surgical, no big rewrite)

1. **Expose resolution outcome on positions API**  
   Already have `matchedBy` and diagnostics; ensure every position response includes a clear `marketSlug` when resolution succeeded (and optionally `resolvedMarketId`) so the UI can show “View market” only when slug is present.

2. **Store SyncedMarket.id on DerivedPosition when resolved**  
   We already write `marketId` (which may be our id or conditionId). Add a separate `syncedMarketId` (nullable FK) set only when resolution by id or conditionId or assetId succeeds; keep `marketId` as the raw value from fills for debugging. Then APIs can rely on `syncedMarketId` for joins and slug lookup without re-resolving.

3. **Document CLOB “market” semantics**  
   In code comments or a small doc, state that UserOrder.market and UserFill.market are the CLOB value (typically conditionId) and must be resolved to SyncedMarket.id for joins. Reduces future confusion.

4. **Portfolio intelligence / dashboard**  
   When showing “near resolution” or “exposure by theme”, use only positions that have a resolved market (endDate present). For unresolved positions, show a “Market not in catalog” or “Sync markets to see details” message instead of inferring endDate.

### Later improvements

- Paginate L2 orders and trades; backfill and store full history for cost basis and compliance.
- Add realized PnL (and optionally last fill timestamp) to DerivedPosition once we have a clear source (e.g. closed position events or reconciled history).
- Add a small “market resolution” cache or table keyed by (conditionId, assetId) → SyncedMarket.id/slug so we don’t repeat resolution in hot paths.
- Consider storing Gamma’s market `id` (if stable) in SyncedMarket for external API calls that expect it.

## 9. UI dependencies on partial / inferred / unstable data

- **Portfolio page** (`app/(dashboard)/portfolio/page.tsx`): Uses `/api/portfolio/positions`. Displays `marketId`, `marketTitle`, `endDate`, and links; if enrichment failed, `marketSlug` is null and linking to market detail is not possible. Position alerts filter by `marketId` and `assetId`; if `marketId` is conditionId, alert grouping may not match other screens that use internal id.

- **Dashboard widgets (overview, intelligence, behavior flags):** Overview and behavior flags use snapshot and flags that are keyed by funder; no direct market id ambiguity. Intelligence uses DerivedPosition + SyncedMarket for endDate and concentration; positions without a resolved market (no endDate) are still counted in concentration by theme/category from DerivedPosition’s heuristic category/theme.

- **Market detail page** (`app/(dashboard)/markets/[slug]/page.tsx`): Loads by **slug**; all data (positions, fills, orders, signals) is joined by `market.id` and assetIds. Positions are fetched by assetId and funder; if a position’s stored marketId is conditionId and doesn’t match this market’s id, that position won’t appear on this market’s page even if it’s the same market. So positions that failed resolution by id/conditionId/assetId won’t show on the correct market detail.

- **Recommendations:** Built from SyncedMarket rows; MarketSignal.marketId is always our id. Safe for internal joins. Recommendation detail and “go to market” links use slug from MarketSignal or market lookup; consistent as long as we use our id → slug from SyncedMarket.
